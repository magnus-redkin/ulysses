# Архитектура Multi-Gate маршрутизации через SOCKS5 и socat
# Дата: 2026-07-25

## Общая схема потока данных

Клиент (App Hiddify) → Gate:443 (HAProxy, TCP) → WireGuard → HFM:4430X (HAProxy, TCP)
  → socat:3530X (TCP) → Xray:35221 (Reality xHTTP) → routing по source IP
  → SOCKS5 Dante на гейте → Интернет

## Пошаговый разбор

### Шаг 1: Клиент → Гейт

Клиент подключается к гейту по протоколу VLESS Reality xHTTP.
Порт: 443 (стандартный HTTPS).
Трафик шифрован внутри TLS как обычный HTTP/2 (xHTTP transport).

### Шаг 2: Гейт → HFM (WireGuard)

HAProxy на гейте принимает TCP:443 в режиме mode tcp.
HAProxy НЕ терминирует TLS, НЕ добавляет PROXY Protocol.
HAProxy форвардит TCP-поток через WireGuard-туннель на HFM:
- G-1: 10.90.0.11:44301
- G-2: 10.90.0.12:44302
- G-3: 10.90.0.13:44303

WireGuard обеспечивает шифрованный туннель между гейтом и HFM.
IP гейта в WireGuard: 10.90.0.3 (G-1), 10.90.0.4 (G-2), 10.90.0.5 (G-3).
IP HFM в WireGuard: 10.90.0.1.

### Шаг 3: HAProxy на HFM → socat

HAProxy на HFM слушает три порта:
- gate1: 10.90.0.11:44301 → 127.0.0.1:35301
- gate2: 10.90.0.12:44302 → 127.0.0.1:35302
- gate3: 10.90.0.13:44303 → 127.0.0.1:35303

HAProxy работает в mode tcp, без accept-proxy, без send-proxy.
Просто пересылает TCP-байты на локальный порт socat.

### Шаг 4: socat → Xray Reality

socat слушает три порта на loopback:
- 127.0.0.1:35301 → 127.0.0.1:35221 (source IP: 127.0.0.11)
- 127.0.0.1:35302 → 127.0.0.1:35221 (source IP: 127.0.0.12)
- 127.0.0.1:35303 → 127.0.0.1:35221 (source IP: 127.0.0.13)

socat — это внешний процесс (не внутри Xray), который создаёт реальное
TCP-соединение через сетевой стек Linux. Благодаря этому Xray видит
source IP = 127.0.0.11/12/13, а не IP клиента.

Xray Reality inbound слушает на 127.0.0.1:35221.
Настройки Reality: network=xhttp, mode=auto, security=reality,
dest=dl.google.com:443, path=/TZe1DA5Xmdguu8htyuGgnt.
acceptProxyProtocol: false (socat форвардит чистый TCP).

### Шаг 5: Xray Reality обрабатывает VLESS

Xray расшифровывает VLESS, проверяет UUID пользователя,
извлекает целевой запрос (например, youtube.com:443).

UUID пользователей управляется HFM автоматически.
Список клиентов находится в 05_inbounds_02_reality_main.json.

### Шаг 6: Routing по source IP

Xray применяет правила маршрутизации из 03_routing_gates.json:
- source 127.0.0.11 → outbound socks-g1 (Dante на G-1, 10.90.0.3:1080)
- source 127.0.0.12 → outbound socks-g2 (Dante на G-2, 10.90.0.4:1080)
- source 127.0.0.13 → outbound socks-g3 (Dante на G-3, 10.90.0.5:1080)

Ключевой момент: source IP определяется по тому, какой socat
обработал соединение. Socat G-1 биндится на 127.0.0.11,
socat G-2 — на 127.0.0.12, socat G-3 — на 127.0.0.13.

### Шаг 7: SOCKS5 → Dante → Интернет

Xray устанавливает SOCKS5-соединение с Dante на соответствующем гейте.
Dante принимает запрос и выходит в интернет через внешний IP гейта.
Внешний сайт видит IP гейта, а не IP HFM.

### Шаг 8: Ответ → Клиент

Ответ от сайта возвращается по тому же пути:
Интернет → Dante → SOCKS5 → Xray → socat → HAProxy → WireGuard → HAProxy на гейте → Клиент.

Каждый этап работает поверх TCP, соединения терминируются и создаются заново
на каждом шаге. Асимметричной маршрутизации не возникает.

## Почему нельзя сделать проще

### Проблема 1: Один Reality inbound на всех

HFM управляет пользователями и генерирует ТОЛЬКО один Reality inbound.
Нельзя создать три Reality inbound с разными тегами для routing,
потому что HFM перезапишет конфиг при добавлении пользователя.

### Проблема 2: Dokodemo-door не работает с xHTTP

Пробовали направить трафик через dokodemo-door внутри Xray.
Но xHTTP использует HTTP/2 фреймы. Dokodemo-door передаёт байты
внутри памяти процесса Xray, ломая структуру HTTP/2.
Xray не отвечает на такие соединения.

### Проблема 3: PROXY Protocol стирает IP гейта

HAProxy может добавлять PROXY Protocol с реальным IP клиента.
Но для routing нам нужен IP гейта, а не клиента.
Xray после acceptProxyProtocol видит IP клиента, не гейта.
Routing по source IP не работает.

### Проблема 4: iptables CONNMARK не работает

Пробовали маркировать входящие соединения через iptables CONNMARK.
Но HAProxy терминирует TCP от гейта и создаёт новое соединение с Xray.
Xray создаёт третье соединение для outbound.
Связь между сокетами теряется, CONNMARK не передаётся.

### Проблема 5: WireGuard AllowedIPs

Нельзя использовать один WireGuard-интерфейс с тремя пирами
и разными AllowedIPs для routing. WireGuard выбирает одного пира
для диапазона 0.0.0.0/0, игнорируя маршрутизацию.

## Почему socat работает

socat — внешний процесс, создающий реальное TCP-соединение
через сетевой стек Linux. Xray видит source IP = IP socat.
Благодаря разным source IP (127.0.0.11/12/13) Xray может
различить гейты через routing по source.

Это единственный найденный способ, который:
- Не требует изменения логики HFM
- Не ломает xHTTP транспорт
- Не зависит от PROXY Protocol
- Позволяет routing внутри Xray по source IP

## Конфигурационные файлы (HFM)

/opt/hiddify-manager/xray/configs/05_inbounds_02_reality_main.json
  Reality inbound на 127.0.0.1:35221, acceptProxyProtocol: false

/opt/hiddify-manager/xray/configs/06_outbounds_socks.json
  Три SOCKS5 outbound: 10.90.0.3:1080, 10.90.0.4:1080, 10.90.0.5:1080

/opt/hiddify-manager/xray/configs/03_routing_gates.json
  Routing: source 127.0.0.11→socks-g1, 127.0.0.12→socks-g2, 127.0.0.13→socks-g3

/opt/hiddify-manager/haproxy/haproxy.cfg
  Три gate: 44301→35301, 44302→35302, 44303→35303
  (добавлены в конец родного конфига HFM)

/etc/systemd/system/socat-g1.service
/etc/systemd/system/socat-g2.service
/etc/systemd/system/socat-g3.service
  Systemd-сервисы для socat

## Конфигурационные файлы (Гейты)

/etc/haproxy/haproxy.cfg
  frontend на *:443, backend на 10.90.0.X:4430X (через WG)

/etc/wireguard/wg0.conf
  WG-туннель к HFM, AllowedIPs = 10.90.0.0/16

/etc/danted.conf
  SOCKS5 прокси на порту 1080, без авторизации

/etc/systemd/system/danted.service.d/restart.conf
  Авто-перезапуск при падении

## IP-алиасы (HFM)

Необходимы для HAProxy и сохраняются после ребута:
- 10.90.0.11/32 на hiddifywg (для HAProxy gate1)
- 10.90.0.12/32 на hiddifywg (для HAProxy gate2)
- 10.90.0.13/32 на hiddifywg (для HAProxy gate3)
- 127.0.0.11/32 на lo (для socat source)
- 127.0.0.12/32 на lo (для socat source)
- 127.0.0.13/32 на lo (для socat source)
